# Moving from Static Prototypes to Interactive Ones

*Maksim Tcvetkov · Product Design and Security Lead*

Designers who draw out websites page by page in Photoshop are becoming less and less in demand. Specialists who keep drawing nothing but static comps, creating a pile of problems for themselves and for developers alike, get hired very reluctantly these days. Plenty of business owners have already been burned, and understand that 90% of web projects don't turn a profit, and that poorly thought-out web projects down the line become an endless source of headaches and marketing spend. But good designers who actually care about their clients need to reach into the front end and build their own ideas with their own hands. Most of the problems a client will run into — badly thought-out usability, above all — are easy to catch in an interactive prototype. And an interactive prototype needs to happen as fast as possible: build it, show it, build it, show it — which is why we won't be considering Axure here. Like any sufficiently complex tool, Axure makes it very easy to slide into excessive detail.

A related, practical note before moving on: plenty of designers still end up in Axure regardless, and one recurring annoyance is the browser-extension requirement for viewing prototypes. If you'd rather skip installing it, open `C:\Program Files (x86)\Axure\Axure RP Pro 8\DefaultSettings\Prototype_Files\start.html` and delete these lines:

```javascript
$(window).bind('load', function() {
  if(CHROME_5_LOCAL && !$('body').attr('pluginDetected')) {
    window.location = 'resources/chrome/chrome.html';
  }
});
```

And on passing data between pages in Axure specifically — logins and passwords between screens, say — that's handled through Global Variables, though they only work within Axure itself; there's no way to pull a value in from outside (aside from the date). Say you've built the fairly standard login/password-check logic every prototype like this uses: create the variables you need under Project > Global Variables, then select the text fields the user will type into, build the relevant Case, and add a Set Variable Value action. On the page you're passing that data to, use the "OnPageLoad" action, add a "Set Text" action to the block whose text you want to change, and choose "fx" — in the window that opens, select the text that should change, click "Insert Variable or Function…" and choose your variable from the resulting list.

Many designers complain they have no tool for prototyping a genuinely fluid, interactive, responsive layout. Learning to write code from scratch isn't realistic given how busy they already are. And the situation only gets worse when you're designing with a chatty client looking over your shoulder, needing pages built at the speed of thought, across multiple resolutions. So what do you do? Use Bootstrap. Fortunately, web developers are lazy enough that they've optimized a huge share of their own workload already. There's a development environment that lets you drag Bootstrap components into place with the mouse. It's the scary and laggy Dreamweaver, and it lets you quickly design sites using Foundation/Bootstrap plus SASS/LESS. You'll be able to build fully responsive sites, and pick up the habit of building valid layouts on a proper *grid*. So, the fastest path: create a new project (the "Include a pre-built layout" checkbox controls whether the document starts with ready-made template markup — you can remove it):

*Building media blocks*

**Media queries are a good thing.** With the document created, you can drop in a pile of components from Bootstrap and jQuery (the Insert and Snippets tabs). The responsive CSS grid, CSS utilities, and glyphicons are especially worth a look — the nicest parts of the toolkit. Since we need to design for different screen resolutions, let's turn straight to Visual Media Queries — the colored lines beneath the "Code," "Split," and "Live" buttons. They let you attach CSS to different screen sizes within media queries. The color coding: green marks the maximum width, blue marks the range between minimum and maximum width, and purple marks the minimum width. To build your own media query, click the triangular "+" icon; once you've created and saved a new CSS file (give it a meaningful name!), right-click your media query bar and choose Go To Code, then write your CSS. What comes out the other end is markup you can bolt straight onto ModX.

You don't have to write CSS by hand, though — you can enter values through the CSS Designer panel (see the image on the left). Choose the right CSS file under the @Media section, and in the panel below (Selectors), click the plus icon — done, you've created a selector, and now you add properties to it in the Properties panel. In CSS, a class selector is marked by the name following a dot (.), and an ID selector by the name following a hash (#). This is how you can design a mobile version of a site, even though mobile remains the most inefficient platform out there.

Related, and worth answering now that browser testing has come up: how do you actually test your markup across different browsers? A Windows VM works well, using one of the semi-free Windows evaluation builds. If you'd rather pay, BrowserStack or Sauce Labs handle it; on a Mac, Remote Desktop is another option. When testing, the browser that actually deserves your attention isn't IE — it's Safari. IE8 and IE9 combined account for around 1% of the average social network's audience these days.

[![Windows scaling in a browser](https://your-scorpion.ru/wp-content/uploads/2017/05/drop_dreamweaver.png)](https://your-scorpion.ru/wp-content/uploads/2017/05/drop_dreamweaver.png)

The question of scaling gets solved with the `viewport` meta tag, which lets content render relative to the screen's actual width. You can set values manually (better not to), though the far more common approach is `<meta name="viewport" content="width=device-width, initial-scale=1.0">`. The browser needs to know the viewport's width — sometimes that's measured up to the scrollbar, sometimes past it. You can set width in pixels relative to the device's real width, or disable scaling entirely with `user-scalable`. There's also a `device` prefix for targeting width and height — this accounts for the device's own dimensions rather than the browser window's. And the `orientation: landscape` parameter lets you apply unique CSS properties specifically in landscape orientation.

When we talk about web apps, it's worth understanding that pixels come in different flavors. Hardware pixels are the physically real pixels on the display panel. There are also device-independent pixels, which additionally factor in the physical size of the screen the design is shown on. CSS pixels can equal either hardware pixels or device-independent pixels, depending on context — sometimes you need to establish the ratio between the two using CSS or JS.

Worth a quick detour here: HTML was originally built around a relative coordinate system, and absolute positioning is a relatively recent addition — whereas any vector editor is built entirely around absolute positioning, with full control. That's exactly where the sharp difference comes from between building layouts in code and building them in a design editor.

Reworking a prototype into a proper design: CSS Designer holds an All tab and a Current tab — the All view isn't sensitive to whatever's selected in the design canvas, while the Current tab lets you work with a single selected element. Customizing the visual appearance isn't hard, and leaving Bootstrap's default component styling untouched is bad form. So create a `bootstrap_skins.css` file and start overriding the defaults to match your own taste. You can do this by hand, in the code editor plus the browser inspector — as you change selectors, related elements highlight in the layout, so every change stays predictable. Dreamweaver can only open websites built with Bootstrap version 3 or later. And if you want to ship your suddenly-working project to production, bypassing a dedicated developer entirely, the [ModX](http://modx.ru) engine plus Bootstrap is a solid combination — MODX Evolution is the easiest way to get a template running on that CMS.

But working in Dreamweaver is a dubious pleasure, so there's a whole other cluster of programs for generating HTML — a set of tools from Adobe specifically. **Muse, Edge, Inspect, Animate, and Reflow.** This software builds responsive or fixed layouts without ever looking at code, designed for people who want to draw adaptive layouts for every screen at once. Work out your percentages, build your responsive layout, and the code that comes out the other end is just a bonus. You can build a fluid layout in Reflow or a static one in Muse, export it into Dreamweaver, finish the code by hand, and drop in animations built in Animate and Edge. Or reach for other tools entirely, like Pinegrow, Webflow, Macaw, or Webydo. But the tool itself isn't really the point — you'll always be working with elements and their properties, and those properties are identical across every editor listed above, since browsers render sites based on exactly those properties. Let's walk through the core ones (using Reflow as the example).

[![Reflow interface example](https://your-scorpion.ru/wp-content/uploads/2017/05/reflow_job.png)](https://your-scorpion.ru/wp-content/uploads/2017/05/reflow_job.png)

**1.** Set a block's size — it can be in percentages, pixels, em, or auto. Percentages are simple enough to grasp: if the parent block is 200px wide, 50% equals 100px. EM is harder to get a handle on. Example: a page sets its font size to 14px; 1em equals 16px, 2em equals 28px, and so on — by default, browsers treat 1em as 16px, and setting either `font-size: 100%` or `font-size: 1em` on the body gives the same result.

Which unit should you actually pick? It's fairly logical: if the task is building a site for one specific resolution, pixels are the right fit. But if you want the site to look good across different resolutions, em and percentages are the better choice.

A related, worthwhile extension on units, since the article's own list above only scratches the surface: pixels are the standard everything else resolves to — even a value like `0.8rem` gets recalculated into whole pixels under the hood. The units below exist purely for responsive layout, for flexible relationships between elements, and for making spacing and scale depend on the site's own dimensions.

Among relative units, **%** (percent) depends on every property of the parent — set `font-size: 200%` on a parent, and text in nested blocks doubles in size. This doesn't work with `margin`, `line-height`, or `width`/`height` on fixed blocks.

A second good unit is **em**, also relative — it depends on the parent's `font-size`. If a button's text size is set in em and that button sits inside a block of running text, the button adapts to that surrounding text's size. So `line-height: 1em` equals 16px if `font-size: 16px` is set.

A third good unit is **rem**, which depends on the root `font-size` and lets you adapt a layout for tablets — just change the `font-size` on `<html>`, and nothing else needs redefining (in an ideal scenario).

Among the less-known units: **vw, vh, vmin, vmax**, all relative to the viewport. They behave in an interesting way — 1vw equals 1/100 of your browser window's actual width. vmin and vmax track the browser window's shorter dimension — if width is smaller than height, vmin tracks width. This raises a real dilemma: vw, vh, or percent? Percentages tend to work better for width, since they respond to exactly the portion of the layout that matters; for height, vh tends to be the better fit than percent.

Where does this actually get used? On slide-style sites, the kind Oleg Chulakov builds, say — set 100% width and 100vh height, and you get slides where a single block fills the entire visible viewport. You can build modal windows the same way: 50% for the popup itself, 100% for the backdrop behind it.

That's the ideal case. In practice, designers working without a sharp design director end up building rigid layouts for phone and desktop where nothing scales cleanly by a quarter. In cases like that, relative units might not be the right fit at all — but converting relative units across platforms is still easier than the alternative.

Other units worth knowing: mm (millimeters) = 3.8px, cm (centimeters) = 38px, in (inches) = 96px, pt (typographic point) = 3/4px, pc (typographic pica) = 16px.

*(A quick follow-up worth including here too: are modern designs simply easier to lay out in vw across the board? In an ideal world, yes. In practice, plenty of clients run browsers with a pile of vertical panels, or page zoom set to 150–200%, and everything drifts. So vw tends to suit sites where text specifically needs to grow as the layout stretches wider — since 1vw always equals 1% of viewport width.)*

**2. max-height, max-width, min-height, min-width** set an element's maximum or minimum width/height. The logic: if the content's width would be less than `min-width`, the element's width becomes `min-width` instead. If the content's width would exceed `max-width`, the block's width becomes `max-width`. Otherwise, the block's width simply matches its content.

**3. Margin.** Sets the spacing outside an element's edge (either on every edge at once, or on a specific one). Margin is the distance from the current element's edge to its parent's inner boundary.

**4. Padding.** Sets the distance from an element's inner border edge to the imaginary rectangle bounding its content — the space around the content inside the element.

**5. Visibility.** The `hidden` value hides a block while still leaving empty space where it would have been (unlike `display: none`).

**6. Position.** Read this one carefully — it's genuinely important. The `fixed` attribute behaves a lot like `absolute`, but the difference is that `fixed` anchors to the `left`, `top`, `right`, and `bottom` properties relative to the screen itself, and doesn't move when the page scrolls — like an ad banner. A block with `position: fixed` can't be anchored inside another block. A `fixed` element also can't stretch its content. The `relative` attribute positions an element relative to its original position. `static` is positioning with no special behavior at all.

**7. Display.** Turns layout elements block-level or inline. Block elements create a rectangular area filling their parent's full width (adjustable via `width`), and you can place elements of any type inside a block element. Inline elements sit one after another without acting as blocks, and can't have a size assigned to them directly.

**8. Float.** Which side an element aligns to, which side it presses against its parent, and which side other page elements will wrap around. Float is how you build "floating" elements and set up columns without a table. Float pushes a block left or right along the current line.

**9. Clear.** Prevents other elements from wrapping around a given side of an element.

**10. Overflow.** Governs how a block's content behaves once it exceeds that block's own height or width. Only applies to block-level elements.

> `line-height: 1.5` is generally considered the most readable value for 16px text.

A related, precise problem worth walking through here, since it comes up constantly between design handoff and production: text that's perfectly built to the pixel in the mockup still ends up with mismatched minimum spacing around it once it's in production. Telling a developer "the button needs `font-size: 16px` with text centered" isn't enough on its own to guarantee a good result. `line-height`, when given no unit, is calculated relative to the chosen `font-size`, but the alignment of that `font-size` depends on the container, which is itself set by em-based font parameters.

![Baseline alignment illustration](https://your-scorpion.ru/wp-content/uploads/2017/08/shot_170802_124655-2.png)

The obvious first instinct is correcting this with `vertical-align`. Vertical alignment is relative, since lines occupy a page from top to bottom, with each line's edges butting up against the next vertically. `vertical-align` governs an element's position within a line relative to the other elements on that same line, and lets you change the content's height within the line. The default value is `baseline`, but `vertical-align: middle` is the generally recommended one. That looks like a fix, but it won't actually get you the result you want — `middle` aligns the box's vertical center with the parent box's baseline plus half the parent's x-height, and baseline positions vary depending on context.

To actually solve this, you need to settle on which baseline you're working from. Fonts carry their own metrics — ascender height, descender height, x-height, capital height, and so on — and all of them affect where the baseline actually sits.

The height of a content area is determined by its content. If an area holds only text, its height is determined by the font's own metrics. There's a second, invisible height too, governed by `line-height` (which defaults to `normal`), and that governs how the height of the line's container gets calculated.

![Line-height container illustration](https://your-scorpion.ru/wp-content/uploads/2017/08/DocumentWait-1.png)

In other words, `line-height` isn't the distance between a font's baselines — it builds an invisible area instead. In standard terminology, `line-height` is your leading. It's split 50/50 above and below the content, which is why content always sits centered within that invisible area.

![Content centered within the invisible line area](https://your-scorpion.ru/wp-content/uploads/2017/08/shot_170802_130721-2.png)

Where you need alignment relative to the invisible area around the main container, `vertical-align: top` / `bottom` aligns to the top or bottom of the line's container, and `vertical-align: text-top` / `text-bottom` aligns to the top or bottom of the content area itself. That distinction is the crucial nuance in how `line-height` and `vertical-align` actually interact.

![Vertical-align nuance illustration](https://your-scorpion.ru/wp-content/uploads/2017/08/идеи.png)

How do you actually calculate a good `line-height`? On one font from my own machine, the em-square is defined as 1920 units at `font-size: 100px`, with an ascender height of 1728, a descender height of 402, and an inter-line gap of 74. That means at `font-size: 100px`, the content area's height works out to 1728 + 402 = 2130 — so 2130/1920 = 1.109, meaning the content area's height is 110px. For `line-height`, it's 1728 + 402 + 74 = 2204, and 2204/1920 works out to 115px.

So `line-height: 1` is genuinely the wrong call — in most cases, a value greater than 1 is correct. There are beginner-level formulas floating around too, like text height × 1.3 or × 1.5, but those are strictly for juniors. There are three popular approaches in practice: calculating from the font's actual baseline (genuinely difficult), calculating from line-height directly, or simply not bothering with any of it at all.

And a `<div>` is really just a wrapper, nothing more. As the natural endpoint of learning everything above, you'll eventually move on to writing plain markup by hand in a text editor. Over time, you might even move from Bootstrap to Foundation 6 — but that's an entirely different story. What matters is speed, and your own knowledge.

My current setup: Gulp as the project bundler, the BEM methodology, Stylus as the CSS preprocessor, and Jade as the HTML templating engine. But if you're not ready to start learning to build layouts by hand, take a look at [Hype](http://tumult.com/hype/) — it's well suited to the web (everything's responsive), has a proper timeline, and exports clean, solid HTML5. You can drop in your own JS and manually tune animation curves. If your team works in React, try [React Structor](https://github.com/ipselon/structor) — they'll like it.

---

All well and good — but you don't like this approach, or you don't want to learn to build layouts, or you don't have the time, or your art director won't accept working this way, or it just doesn't fit what you're doing? There's a second path: keep generating static images and uploading them to online services, and build GIFs too (GifCam helps here, along with [GifGun](http://extrabite.cc/gifgun) for After Effects and [Apple's own equivalent](https://developer.apple.com/videos/wwdc/2015/?id=803)). Take a look at this general [comparison](http://www.cooper.com/prototyping-tools) of prototyping tools and pick whatever suits you. In the end, you'll likely settle on one or two tools plus Confluence (a wiki system) for the more complex tasks. For simple tasks, single-page-application tools work great — NinjaMock, [balsamiq.com](http://balsamiq.com/), [moqups.com](http://moqups.com/), [mockflow.com](http://mockflow.com/), [hotgloo.com](http://hotgloo.com/), [pixate](http://www.pixate.com). And if you need to prototype a single page yourself, Atomic or Framer are the tools to reach for.

There's an even simpler route for anyone who enjoys sketching mobile apps by hand. For the earliest stages of mobile design, it genuinely helps to draw the interface on paper — it engages hand motor memory directly and helps you rule out obviously bad decisions right away. Building navigation flow maps is your responsibility toward the developers, the same as [image slicing](https://your-scorpion.ru/automator_image_crop/) — there's no need to hand either of those to the client. You can perfectly comfortably live with services that turn static images into a dynamic mockup by letting you mark tap or transition zones directly on those images. What comes out is a mockup that's genuinely close to the final product.

Where should you actually draw mobile app designs — Photoshop or Sketch? Sketch's pros and cons: you can use symbols, and symbols nested inside symbols, for repeating elements (a genuinely strong advantage). Import support, unfortunately, is weak. Sketch has the CRAFT plugin, which lets you build app prototypes directly inside Sketch, and the Auto-Layout plugin, which resizes layouts across different screen sizes. You already know everything about Photoshop, and it can't claim anything comparable. In mobile apps, it isn't enough to just draw the screens — you need to test the navigation logic too. There are services built specifically for marking transition zones. The simplest of these is [POP](https://popapp.in), which lets you photograph a paper prototype and mark transition areas directly on it. Good for brainstorms, not much beyond that. For serious mobile prototyping, Marvelapp and InVision are the standard choices. Let's compare them a bit:

**InVision** is very simple, and you can share a prototype via link. Great for collaborative work, since comments can carry file attachments — InVision's commenting mode is close to a gold standard. Limited animation support, and the free tier only allows three projects. It has version control (!), project statistics, integration with several popular project-management systems, and support for Retina layouts. For service design work (with development cycles running two-plus years), it's an excellent fit — the design studio Fjord uses it heavily. InVision integrates with Sketch: you just save the document, and the artboards are already in the prototype. In the US, plenty of teams have shifted to Illustrator + InVision. It supports Photoshop artboards and lets you publish straight to Dribbble.

**Marvelapp** links screens visually rather than through a dropdown menu (unlike InVision), but commenting and team collaboration are both still fairly weak. It's 90% free, and you can create an unlimited number of projects. Excellent for iOS-specific design work. You can edit tap zones directly from your phone, and Marvelapp also lets you draw wireframes. On the downside, there are no customizable controls. Bottom line: a great service for a solo designer or a small team. It eats `.sketch` artboards as individual screens just as well as InVision does, with direct Dropbox sync. A useful tip: build your prototype in "modules" (main screen, inbox, outbox, chat window) and link them together — this makes projects with 400+ screens actually manageable.

**Proto.io** is a platform for building interactive mobile-app prototypes with support for every major user gesture. It lets you run finished prototypes on real devices, with full gesture and device-format support. It handles screen hierarchy very well, and comes with component libraries. It can work with variables too. For usability research specifically, Proto.io is generally the best place to hand off a prototype.

**Principle is genuinely worth learning.** It's built for animation, and it's simple and logical, with a timeline and flexible animation-curve tuning. It supports Sketch imports. It lacks conditional logic and link-based previews, though — on a phone, you can only view a prototype over a cable. Good for micro-animations and transitions between states and screens. **Flinto** looks a little nicer, with Live Preview and link-based prototype sharing, though it lacks a timeline. Flinto makes it easy to draw connections between elements in a layout (built elsewhere beforehand), and pushes the prototype to any device's home screen directly.

There are other animation tools too: [Origami](http://origami.design/), [ProtoPie](https://www.protopie.io/), [Framer](https://framerjs.com/), and others. ProtoPie and Framer both support a mobile device's built-in sensors — accelerometer, gyroscope, microphone, camera, 3D Touch — which matters for prototyping certain kinds of apps. You can even use actual code for mobile prototyping now; it's genuinely not much harder than dedicated prototyping tools these days. Flutter and nuxt.js are worth a look here.

A natural follow-on question, since code-based prototyping came up: is something like React Native genuinely capable of fully replacing native mobile development? It depends entirely on the business need. All React Native really promises is code that runs on both major mobile platforms at once — much like Unity in the gaming world, which compiles games from a single environment to every platform with light adjustments. For large-scale B2C work, I wouldn't reach for React Native — it isn't suited to AR/VR either. If you only need to build for a single mobile platform, there's no real reason to use it. It also isn't great for working with third-party devices — printers, smart-home hardware, routers. And if your project leans heavily on graphics with serious performance demands, React Native won't be your best option. For B2B apps, though, it's a genuinely solid choice.

A related question worth folding in here too: is there a way to build UI once and target every platform at once — not just React scaling across mobile and desktop, but a genuinely broader approach that covers games as well? Scaleform used to be a solid answer here, but Autodesk discontinued it, though you can still find AS3 + Scaleform projects floating around. Among current options, Coherent (JS) and Noesis (C#) are both worth a look — both integrate with UE4, though both affect frame rate. NoesisGUI is worth a glance too. If your interface is built on Unity from the start, Doozy is worth checking out specifically for managing screen transitions and color, and DoTween works well alongside it for animation.

![Comparison chart of prototyping and animation tools](https://your-scorpion.ru/wp-content/uploads/2015/07/6373.png)

Unfortunately, no single perfect tool for prototyping and animation actually exists. My own pipeline runs Webflow for websites, Proto.io for usability research, Pixate for micro-animations, and Principle for everything else interface-related. So: prototype early and often. Love minimal. Work at maximum.

One more natural extension worth adding here, since it comes up constantly now that Figma dominates this space: what are the actual alternatives for genuinely testing prototypes with real user data, given that Figma itself doesn't collect user data from its own prototypes, Marvel lacks drag-and-drop interaction, and services like Maze and Useberry get expensive fast? You can bolt data-collection systems onto Figma prototypes directly — PlaybookUX.com and Methinks.io both work well for this. Preely.com is genuinely solid too (I've used it with a Sketch import), and lookback.io is the standard, reliable choice. For recruiting respondents, either build your own pool or use respondent.io.
